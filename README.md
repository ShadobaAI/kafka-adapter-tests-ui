# 1С: Адаптер Kafka — UI-Тесты

![Платформа](https://img.shields.io/badge/1С-8.3.21+-blue)

Набор UI-тестов для проверки поведения [1С: Адаптер Kafka](https://github.com/ShadobaAI/kafka-adapter).

## Назначение

Репозиторий содержит тесты для проверки изменений адаптера:

- **UI-тесты Vanessa Automation** — сценарии в каталоге `features`, которые проверяют поведение адаптера через интерфейс пользователя;

> Репозиторий предназначен только для разработки и проверки изменений адаптера. В промышленную эксплуатацию не поставляется.

## Инструменты

- [Vanessa Automation](https://pr-mex.github.io/vanessa-automation/) — UI-тесты для проверки пользовательских сценариев.

## Работа через ИИ

Используется навык `vanessa-ui-tests`, общий [Vanessa MCP toolkit](../../tools/ai/ui/README.md)
и коллекция `vanessa` установленного MCP `v8std`. Во время работы исходные
репозитории и сайт документации Vanessa не требуются.

Локальный профиль хранится в `.vanessa/profile.json` и не попадает в Git.
Он связывает общие команды с основной базой контура `kfk-edt`, платформой,
runtime и этим каталогом features. Параметры подключения задаются без пароля.

Для команд нужен Node.js в `PATH`. Перед первым запуском создайте локальные файлы
из [шаблона профиля](../../tools/ai/ui/profile.example.json)
и [шаблона интерактивных настроек](../../tools/ai/ui/interactive.example.json).
Если этих файлов ещё нет, выполните из корня репозитория:

```powershell
New-Item -ItemType Directory -Path .vanessa -Force | Out-Null
Copy-Item ../../tools/ai/ui/profile.example.json .vanessa/profile.json
Copy-Item ../../tools/ai/ui/interactive.example.json .vanessa/interactive.local.json
```

В `.vanessa/profile.json` заполните путь к платформе и готовому runtime, базы
менеджера и TestClient, имя клиента и свободный loopback endpoint MCP.
Относительные пути считаются от файла профиля: для этого репозитория задайте
`projectRoot: ".."`, `features: "../features"`, `results: "./results"`
и `runtime.paramsFile: "./interactive.local.json"`. В интерактивных настройках
сохраните `ВыполнитьСценарии` и `ЗавершитьРаботуСистемы` равными `false`.
Подробности полей и настройки серверной базы приведены в
[README toolkit](../../tools/ai/ui/README.md).

Если профиль ссылается на `userEnv`, перед командами задайте эту переменную среды
локально. Имя пользователя не включается в tracked профиль или примеры.
Менеджер и TestClient всегда запускаются в режиме «Такси» (`/iTaxi`).

После заполнения файлов выполните из корня этого репозитория следующие команды.
`configure` читает готовый профиль и выводит TOML-фрагмент настройки MCP:

```powershell
node ../../tools/ai/ui/vanessa.mjs configure --profile .vanessa/profile.json
node ../../tools/ai/ui/vanessa.mjs start --profile .vanessa/profile.json
node ../../tools/ai/ui/vanessa.mjs setup --profile .vanessa/profile.json
node ../../tools/ai/ui/vanessa.mjs doctor --profile .vanessa/profile.json
node ../../tools/ai/ui/vanessa.mjs list --profile .vanessa/profile.json
node ../../tools/ai/ui/vanessa.mjs run --profile .vanessa/profile.json --feature features/Справочники/Брокеры/ОсновныеОперации.feature --scenario 'Начальное состояние новой карточки брокера'
```

ИИ исследует целевую форму, актуализирует feature-файл, проверяет его синтаксис
и запускает затронутый сценарий. Для приёмки нужен успешный прогон с начала
и подтверждение ожидаемых проверок. Исправление теста сохраняет его назначение.
`run` удерживает одну блокировку клиента до получения результата выбранного
сценария. В Single 1.2.043.45 / MCP 1.31 перед следующим запуском иногда требуется
штатный переход из редактора в дерево шагов для получения полного состояния MCP;
навык описывает проверку и восстановление этого состояния.

`VAParams.json` остаётся CI-профилем. Для MCP используется отдельный интерактивный
JSON: без автоматического запуска всех сценариев и завершения 1С. Для первичной
проверки настройки используется сценарий «Начальное состояние новой карточки
брокера», который не записывает данные. Для сценариев с записью заранее определяются
fixtures и стратегия очистки/восстановления, включая сбой. Допускаются собственные
элементы и данные начальной инициализации по правилам [AGENTS.md](AGENTS.md).
Текущие сценарии справочника «Брокеры» создают собственные элементы и после
успешного прогона помечают их на удаление.

`.vanessa/`; CI-настройки — в `VAParams.json`. Отдельные каталоги библиотек и данных
добавляются при появлении экспортных сценариев и файлов fixtures. Имена тестовых
элементов сейчас формируются внутри каждого сценария.

## Функциональные тесты справочника «Брокеры»

Основной функционал справочника и дополнительные операции описывают 32 самостоятельных сценария с тегом
`@Брокеры` в каталоге `features/Справочники/Брокеры`: `ОсновныеОперации.feature`
(10 сценариев), `ПараметрыПодключения.feature` (5 сценариев),
`Блокировки.feature` (1 сценарий), `РедакторПараметров.feature` (7 сценариев),
`ЗащищенныеПараметры.feature` (4 сценария), `ВыборБрокера.feature` (2 сценария)
и `ПраваДоступа.feature` (3 сценария):

| Область | Проверки |
| --- | --- |
| Создание и валидация | Начальное состояние, обязательные наименование, узлы, адрес и ключ параметра; отказ записи неполной карточки |
| Узлы | Добавление, копирование отключённого узла, изменение адреса, флаг использования, сохранение порядка и удаления строк после повторного открытия |
| Запись | Повторное открытие, изменение карточки, отражение изменений в списке, независимость копии, отмена изменений и перечитывание |
| Параметры | Выбор ключа и отмена выбора, значения по умолчанию, строковый, числовой, булев и списочный типы, смена ключа и удаление строки |
| Редактор параметров | Очистка строки, переключение типа редактора, увеличение и уменьшение числа, запрет копирования строки, подбор ключа по уникальной части имени с проверкой единственного совпадения, подсказки без поискового текста и дублей |
| Форма выбора свойства | Текущий ключ, отмена без потери значения, выбор строки, фильтр важности и его сброс, описание свойства |
| Режим пароля | Маскирование искусственного значения `client.id`, сохранение, повторное открытие, изменение и снятие маскирования |
| Защищённые параметры | Отмена редактирования, удаление и повторное добавление ключа, переход к числовому типу, отсутствие переноса защищённого значения в копию и независимость значений копии и исходного брокера |
| Блокировки | Независимость чтения и публикации, сохранение и индикация в карточке и списке, включая оба смешанных состояния |
| Выбор брокера | Выбор собственного тестового брокера в новых карточках продюсера и консьюмера, отмена выбора для пустого и заполненного поля |
| Пометка удаления | Отмена, установка и снятие пометки на собственном тестовом элементе |
| Права доступа | Чтение подготовленного брокера, запрет создания, копирования, пометки удаления, изменения и управления блокировками для `ПользовательKafka` |

Подключение к Kafka не проверяется. Адреса узлов используют домен `.invalid`;
реальные брокеры, пароли и другие учётные данные для этих тестов не нужны.
Запуск проверки подключения, формирование её журнала и окраска узлов также исключены из этого набора.
Проверка числового редактора использует общий параметр `message.max.bytes`:
уменьшение `1024` до `1023`, увеличение `2048` до `2049` и сохранение обоих
значений после повторного открытия. Допустимость значения параметра определяет
пользователь; проверка границ диапазона не входит в требования к редактору.
После сброса фильтра важности проверяются снятый отбор, исходное количество
свойств и наличие всех трёх уровней важности.

Все административные сценарии явно подключают профиль `АдминистраторKafka`
с соответствующим логином, именем компьютера `localhost` и `/iTaxi`.
`ПраваДоступа.feature` подключает профиль `ПользовательKafka`.
Контекст проверяет имя выбранного профиля и параметры
`/N` и `/iTaxi`; произвольный текущий `TestClient` больше не используется.
В среде должны быть подготовлены оба пользователя по [AGENTS.md](AGENTS.md).
В тестах не используются шаги проверки ролей менеджера Vanessa.
Сценарии прав только читают fixture `Брокер по умолчанию` и проверяют
отсутствие команд создания, копирования и пометки удаления в списке,
а также ограничения карточки, не пытаясь изменять общие данные.

В локальном профиле для запуска административных сценариев задайте
`client.name: "АдминистраторKafka"` и отдельную от менеджера переменную
`client.userEnv`, например `VANESSA_UI_ADMIN_USER`, со значением
`АдминистраторKafka`. Для сценариев прав используйте отдельный локальный
профиль с `client.name: "ПользовательKafka"` и `client.userEnv`, например
`VANESSA_UI_READER_USER`, со значением `ПользовательKafka`. Менеджер обоих
профилей остаётся под `АдминистраторТакси`. Перед прогоном `doctor` должен
подтвердить соответствие фактического процесса TestClient выбранному профилю.

Требуется расширение VAExtension, в том числе для проверки состояния объекта
и заключительной пометки тестовых данных на удаление.

Каждый административный сценарий формирует собственное имя `VA-Брокеры-…` из двух случайных
суффиксов и проверяет отсутствие совпадения до создания. Сценарии не выбирают
существующие рабочие элементы и не зависят от порядка запуска. После успешной
проверки созданные записи помечаются на удаление; физически данные не удаляются.
После аварии до заключительного шага могут остаться записи этого прогона:
их имена и шаг сбоя доступны в результатах. Повторный запуск создаёт новый набор.
В сценариях выбора брокера карточка продюсера или консьюмера не записывается; после проверки
изменения отбрасываются. Параметры в режиме пароля содержат только искусственные
строки с префиксом `VA-`. Сценарии сохраняют ожидаемые результаты и при обнаружении
ошибки продукта: успешный синтаксис сам по себе не означает успешного прогона.

Запуск одного затронутого сценария из корня репозитория:

```powershell
node ../../tools/ai/ui/vanessa.mjs run --profile .vanessa/profile.json --feature features/Справочники/Брокеры/ОсновныеОперации.feature --scenario 'Сохранение повторное открытие и изменение брокера'
```

Перед запуском должна быть задана переменная среды, указанная в `userEnv`
локального профиля. Применяется описанный выше переход между Vanessa Editor
и деревом шагов. JSON receipts и исходные результаты прогонов сохраняются
в каталоге результатов локального профиля (`.vanessa/results` для текущей
настройки); они содержат имя сценария, SHA-256 исполненного feature, версии
runtime, итог синтаксиса и результат запуска с начала.

## UI-тесты продюсеров и консьюмеров

Для `кфкПродюсеры` и `кфкКонсьюмеры` сценарии расположены
в каталогах `features/Справочники/Продюсеры` и `features/Справочники/Консьюмеры`.
Теги объектов — `@Продюсеры` и `@Консьюмеры`.

| Файл в каждом каталоге | Пользователь | Проверки |
| --- | --- | --- |
| `ОсновныеОперации.feature` | `АдминистраторKafka` | Чтение подготовленного элемента, его брокера и топика, пустые поля и список объектов/топиков новой карточки, редактирование наименования и отмена создания с проверкой отсутствия элемента в списке |
| `СохранениеИРедактирование.feature` | `АдминистраторKafka` | Создание с записью и отдельный сценарий изменения собственного записанного элемента; повторное открытие по ссылке и проверка реквизитов и табличной части, обновление имени в списке |
| `Параметры.feature` | `АдминистраторKafka` | Выбор ключа из формы свойств librdkafka, добавление и изменение строк, удаление одной строки с сохранением остальных; замена изменённой таблицы стандартными параметрами без дублей, проверка после повторного открытия |
| `ДополнительныеНастройки.feature` | `АдминистраторKafka` | Сохранение включённого и снятого флага дедупликации продюсера или идемпотентной обработки консьюмера; изменение и удаление одной из нескольких строк объектов/топиков с сохранением остальных |
| `Обработчики.feature` | `АдминистраторKafka` | Общие настройки и переопределения строк для произвольного обработчика и Конвертации данных; подтверждение/отмена ввода метода, наследуемое отображение, видимость полей, сохранение неактивных настроек после смены типов |
| `ОтменаИПеречитывание.feature` | `АдминистраторKafka` | Отмена и подтверждение перечитывания, отмена закрытия и отказ от сохранения изменений собственного элемента, итоговое чтение исходных реквизитов |
| `КонкурентноеРедактирование.feature` | Два сеанса `АдминистраторKafka` | Отказ начала редактирования во втором сеансе, проверка текста блокировки и отмена перехвата; сохранение первого сеанса и перечитывание во втором; отдельные сценарии для элементов и диспетчеров |
| `Валидация.feature` | `АдминистраторKafka` | Обязательные реквизиты и строки объектов/топиков, обязательные колонки таблиц, отказ записи с несуществующим брокером; у консьюмера — отклонение нулевого тайм-аута и восстановление предыдущего значения после отмены ввода |
| `КопированиеИПометкаУдаления.feature` | `АдминистраторKafka` | Копирование из списка, перенос настроек, сохранение и независимость копии после повторного открытия; отмена и установка пометки удаления из списка, снятие пометки в карточке с проверкой сохранённого состояния |
| `Блокировки.feature` | `АдминистраторKafka` | Независимость регистрации, сериализации и публикации продюсера, чтения и десериализации консьюмера; все сочетания, запись, колонки списка, отметки команд и предупреждения после повторного открытия |
| `ДиспетчерыЗадач/*.feature` | `АдминистраторKafka` | Чтение подготовленной группы, начальное состояние и отмена создания; создание и изменение с повторным открытием; независимость копии, отмена/установка/снятие пометки удаления; обязательное наименование и отклонение отрицательных счётчиков подпотоков; отмена/подтверждение перечитывания и закрытия; перемещение собственного элемента между своими диспетчерами и в корень |
| `ПраваДоступа.feature` | `ПользовательKafka` | Отсутствие команд создания элемента и диспетчера, копирования и пометки удаления; чтение подготовленного элемента и диспетчера задач в режиме «только просмотр» |

Требуются группа `Диспетчер задач`, `Продюсер: ТестовыйСправочник`,
`Консьюмер: ТестовыйСправочник` и `Брокер по умолчанию`, подготовленные по
[AGENTS.md](AGENTS.md). Сценарии включают плоский режим списка перед выбором элемента,
чтобы не зависеть от раскрытой группы.
Все подключения явно задают пользователя и `/iTaxi` и проверяют выбранный профиль.

Элемент справочника и его группа проверяются отдельно. Группа — диспетчер задач:
в её карточке доступны наименование и число подпотоков обработки/транспорта.
Команд блокировок регистрации, сериализации, публикации, чтения и десериализации
у группы нет; административные сценарии проверяют отсутствие применимых имён команд.
Поля брокера, топиков и параметров элемента не переносятся в ожидания для группы.
Это правило действует для существующих и будущих тестов согласно [AGENTS.md](AGENTS.md).

Сценарии групп используют собственные имена `VA-Диспетчеры-Продюсеры-<суффиксы>`
и `VA-Диспетчеры-Консьюмеры-<суффиксы>`. Ссылки записанных групп и копий сразу
регистрируются для заключительной пометки удаления. После сбоя закрывайте
несохранённые карточки и помечайте только группы этого прогона; подготовленный
диспетчер и его дочерние элементы не изменяйте. Все проверки сохранения, копии и
пометки удаления включают повторное открытие карточки и проверку счётчиков.

Сценарии `ОсновныеОперации.feature` и `ПраваДоступа.feature` не записывают данные.
Проверка отмены формирует уникальное имя с префиксом
`VA-Продюсеры-` или `VA-Консьюмеры-`, проверяет его отсутствие перед созданием
карточки и отбрасывает изменения при закрытии. При сбое нужно закрыть оставшуюся
новую карточку без сохранения; повторная инициализация общих fixtures не нужна.
Сценарии `СохранениеИРедактирование.feature` создают собственные элементы с именами
`VA-Продюсеры-Запись-<суффиксы>` и `VA-Консьюмеры-Запись-<суффиксы>`, уникальными
топиками и идентификатором группы консьюмера. Элементы создаются вне диспетчера задач;
подготовленный брокер используется только как ссылка. Проверяются имя, брокер и
табличная часть; у продюсера — также идемпотентная отправка, у консьюмера — ИД группы
и тайм-аут. Сценарий изменения сначала создаёт и повторно открывает собственный элемент,
затем меняет значения, записывает и открывает его ещё раз. У продюсера меняются имя,
топик и флаг идемпотентности; у консьюмера — имя, ИД группы, топик и тайм-аут.

Сразу после первой записи ссылка регистрируется стандартным шагом VAExtension для
заключительной пометки удаления. После успешной проверки окна закрываются и созданный
элемент помечается на удаление; физически запись остаётся в базе. При сбое закрыть
оставшуюся карточку без сохранения и пометить только элемент этого прогона, определив
его по выведенным в сообщения имени или ссылке (имя может иметь суффикс `-изм`). Если
сбой случился до первой записи, достаточно отбросить несохранённую карточку.
Повторная инициализация общих fixtures не используется. Обмен с Kafka этими
сценариями пока не покрыт.

В `Параметры.feature` каждый сценарий создаёт собственный элемент
`VA-Продюсеры-Параметры-<суффиксы>` или `VA-Консьюмеры-Параметры-<суффиксы>`.
Первый сценарий выбирает дополнительный ключ из формы свойств librdkafka
(`acks` у продюсера, `fetch.min.bytes` у консьюмера), добавляет строку, меняет
значения исходной и добавленной строк, затем удаляет только добавленную строку.
После каждой записи проверяется отсутствие несохранённых изменений; после
итогового открытия — оставшееся значение `message.timeout.ms` или `auto.offset.reset`.
Второй сценарий записывает изменённый набор и восстанавливает стандартную таблицу:
`message.timeout.ms = 5000` у продюсера и `auto.offset.reset = earliest` у консьюмера.
Повторное применение команды не добавляет дубли; результат проверяется после записи
и повторного открытия. Карточка остаётся открытой между изменениями.
Ссылка сразу после первой записи регистрируется для заключительной пометки удаления.
При сбое закройте несохранённую карточку и пометьте только элемент прогона по
выведенным имени или ссылке. Общие fixtures и диспетчеры задач не изменяются;
у диспетчеров нет проверяемых таблиц параметров.

В `ДополнительныеНастройки.feature` снятый флаг проверяется после перечитывания,
установленный — после итогового открытия. Из нескольких объектов/топиков меняется
первая строка, удаляется вторая, затем проверяется оставшаяся строка.
`Обработчики.feature` использует существующие имена методов и настройки Конвертации
данных расширения `examples`, сохраняя их только в собственных карточках.
Сериализация, десериализация и обмен с Kafka не запускаются. Пустые настройки строки
показывают общий обработчик; явные значения строки проверяются отдельно, включая
сохранение неактивных настроек после смены типа и повторного открытия.

В текущей форме поле `РежимАсинх` продюсера и поле `ДвоичныеДанные` консьюмера
скрыты. Сценарии проверяют их скрытость; переключение этих режимов и влияние
асинхронного режима на параметры через данный UI не покрываются.

`ДиспетчерыЗадач/Иерархия.feature` создаёт две собственные группы и элемент.
Элемент создаётся из иерархического списка внутри A; родитель A проверяется до записи.
Затем элемент перемещается в B и в корень. После промежуточных записей
выполняется перечитывание, после последней — повторное открытие.
Ссылки обеих групп и элемента сразу регистрируются для пометки удаления.
При сбое закрывайте несохранённые карточки и помечайте только объекты этого прогона.

`ДиспетчерыЗадач/НепустыеГруппы.feature` создаёт собственные группу, дочерний элемент
и копию группы. Проверяются состав области копии, сохранение счётчиков и исходного
родителя ребёнка. Отмена пометки сохраняет все три объекта; установка и снятие
пометки оригинальной группы каскадируются на её ребёнка, оставляя копию независимой.
Состояние каждого объекта и содержимое ребёнка читаются отдельно на каждом этапе.
Для очистки регистрируются ссылки всех трёх объектов; подготовленные группы не меняются.

Сценарии конкурентного редактирования используют второй профиль
`АдминистраторKafkaПараллельный` с тем же логином и `/iTaxi` на отдельном порту.
Первая карточка остаётся открытой с несохранёнными изменениями. Во втором сеансе
проверяется окно `ObjectBlocking` с сообщением о редактировании в другом сеансе;
команда перехвата не выполняется. После отмены исходные данные сохраняются.
Запись первого клиента подтверждается перечитыванием во втором. Временный клиент
закрывается, подключение возвращается к `АдминистраторKafka`, затем собственный
объект помечается на удаление. При сбое закройте вторую карточку/клиент, отбросьте
несохранённые изменения первой карточки и пометьте только объект по выведенной ссылке.

В `Валидация.feature` каждый сценарий начинает с заполненной собственной новой карточки
`VA-Продюсеры-Валидация-<суффиксы>` или `VA-Консьюмеры-Валидация-<суффиксы>` и изменяет
только проверяемые поля. Сообщения перед каждой попыткой записи очищаются и сравниваются
с точным ожидаемым списком. Проверяются обязательность имени и брокера, ИД группы
консьюмера, непустой список объектов/топиков, тип объекта, ключ и значение параметра
продюсера, топик и ключ параметра консьюмера. Несуществующая ссылка брокера должна
блокировать запись; нулевой тайм-аут — вызывать ошибку ввода до записи.
Перед проверкой пустой таблицы сценарий явно выбирает и удаляет подготовленную строку,
затем проверяет, что количество строк равно нулю. Та же подготовка выполняется перед
добавлением строки с незаполненными обязательными колонками.
После отказа карточка остаётся новой; сценарий отбрасывает изменения и проверяет
отсутствие элемента в обновлённом списке. Подготовленные данные не изменяются.
При сбое достаточно закрыть новую карточку без сохранения. Если обнаружится дефект
и ошибочная карточка запишется, нужно пометить только собственный элемент этого
прогона по выведенному уникальному имени или ссылке; общие fixtures не переинициализируются.
Формат топиков и параметров Kafka этими проверками не валидируется.

В `КопированиеИПометкаУдаления.feature` каждый из двух сценариев создаёт собственный
исходный элемент `VA-Продюсеры-КопияУдаление-<суффиксы>` или
`VA-Консьюмеры-КопияУдаление-<суффиксы>`. Сценарий копирования создаёт также элемент
с суффиксом `-копия`, проверяет перенос брокера, объектов/топиков, параметров и
дополнительных настроек. Затем меняет топик и идемпотентность продюсера либо топик,
ИД группы и тайм-аут консьюмера. После записи проверяет разные ссылки исходника и
копии, оба имени в списке, сохранение изменений копии и неизменность исходника.
Сценарий пометки удаления проверяет отмену и подтверждение команды списка, затем
снятие пометки в карточке. Состояние объекта читается через VAExtension после
повторного открытия по ссылке; имя и настройки также должны сохраниться.
Ссылки исходника и копии регистрируются сразу после записи. В конце оба собственных
элемента помечаются на удаление; в сценарии пометки — один исходный элемент.
При сбое нужно закрыть несохранённые карточки и пометить только собственные записи
этого прогона по выведенным именам/ссылкам. Общие fixtures не изменяются и не
переинициализируются; физического удаления нет.

В `Блокировки.feature` два сценария продюсеров покрывают все восемь сочетаний
регистрации, сериализации и публикации. Сценарий консьюмера покрывает все четыре
сочетания чтения и десериализации. После каждого переключения выполняется команда
«Записать», проверяется отсутствие несохранённых изменений, обновляется список
и проверяются все колонки блокировок (`Р`, `С`, `П` или `Ч`, `Д`). Между списком
и карточкой тест переключается активизацией уже открытых окон. Карточка остаётся
открытой на протяжении всех изменений: используется её существующая блокировка
редактирования. После закрытия формы 1С может удерживать блокировку ещё до 10 секунд.
В карточке для каждого сочетания проверяются отметки команд и предупреждения.
В конце карточка закрывается и один раз открывается по сохранённой ссылке:
повторно проверяются имя, сохранённое состояние всех блокировок и отсутствие
несохранённых изменений. Дальнейшего редактирования после этого открытия нет.
Каждый сценарий использует собственный элемент `VA-Продюсеры-Блокировки-<суффиксы>`
или `VA-Консьюмеры-Блокировки-<суффиксы>`, созданный вне диспетчера задач с исходно
снятыми блокировками. В конце все блокировки вновь сняты, элемент помечается на
удаление. При сбое нужно закрыть несохранённую карточку, снять оставшиеся блокировки
только собственного элемента по выведенному имени/ссылке и пометить его на удаление.
Общие настройки и блокировки fixtures не изменяются; команды обмена не запускаются.

Для запуска используется тот же CLI с административным профилем. Сценарии прав
сами подключают временный TestClient `ПользовательKafka`, проверяют ограничения
в его сеансе, закрывают его и восстанавливают подключение `АдминистраторKafka`.
Так следующий прогон начинает работу с одним административным TestClient.
При сбое до заключительных шагов нужно закрыть временный TestClient и восстановить
административное подключение; данные эти сценарии не меняют.
Например, из корня репозитория:

```powershell
node ../../tools/ai/ui/vanessa.mjs run --profile .vanessa/profile.json --feature features/Справочники/Продюсеры/ОсновныеОперации.feature --scenario 'Начальное состояние новой карточки продюсера'
node ../../tools/ai/ui/vanessa.mjs run --profile .vanessa/profile.json --feature features/Справочники/Консьюмеры/ПраваДоступа.feature --scenario 'ПользовательKafka читает подготовленного консьюмера без возможности изменения'
```

Перед первым запуском новых сценариев выполняется обязательная
проверка настройки сценарием `Начальное состояние новой карточки брокера`.
Оба пользователя должны запускаться без блокирующих стартовых окон. В контуре
с лицензией разработчика платформа может показывать информационное уведомление
при каждом новом сеансе. Его нужно подтвердить до истечения тайм-аута подключения
TestClient; тайм-аут до подключения не является результатом проверки прав.
Новые сценарии требуют проверки синтаксиса в Vanessa и прогона с начала;
наличие feature-файлов само по себе не подтверждает их успешное выполнение.
