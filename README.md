# 1С: Адаптер Kafka — UI-Тесты

![Платформа](https://img.shields.io/badge/1С-8.3.21+-blue)

Набор UI-тестов для проверки поведения [1С: Адаптер Kafka](https://github.com/ShadobaAI/kafka-adapter).

## Назначение

Репозиторий содержит тесты для проверки изменений адаптера:

- **UI-тесты Vanessa Automation** — сценарии в каталоге `features`, которые проверяют поведение адаптера через интерфейс пользователя;

UI-сценарии должны выполняться без реального обращения к Kafka. Доступность
брокера и получение списка топиков относятся к интеграционным тестам YAxUnit.

> Репозиторий предназначен только для разработки и проверки изменений адаптера. В промышленную эксплуатацию не поставляется.

## Инструменты

- [Vanessa Automation](https://pr-mex.github.io/vanessa-automation/) — UI-тесты для проверки пользовательских сценариев.

## Работа через ИИ

Используются навык `vanessa-ui-tests` и CLI установленного плагина 1C AI Core,
а также коллекция `vanessa` установленного MCP `v8std`. Общие правила и профиль
тестирования находятся в `tests/AGENTS.md` и `tests/.ai/` полного Kafka workspace;
при отдельном клонировании UI-репозитория эти файлы в него не входят.

Профиль `.vanessa/profile.json` связывает команды с тестовой ИБ, платформой,
встроенной Vanessa и каталогом сценариев. Он хранится в Git вместе с
интерактивными настройками `.vanessa/interactive.local.json`.
Для CLI нужен Node.js в `PATH`. Формат профиля определён схемой
`schemas/vanessa-runtime.schema.json` установленного плагина 1C AI Core.
Относительные пути в профиле считаются от его файла, а абсолютные зависят
от машины. Менеджер и клиенты должны использовать одну подготовленную тестовую
ИБ unit-контура.

Пример структуры профиля для серверной ИБ; значения в угловых скобках нужно
заменить настройками стенда, а поля `password` оставить пустыми:

```json
{
  "version": 1,
  "id": "tests",
  "projectRoot": "../..",
  "platform": "<путь к исполняемому файлу платформы>",
  "runtime": {
    "navigationUrl": "e1cib/app/Обработка.VanessaAutomationsingle",
    "paramsFile": "./interactive.local.json"
  },
  "manager": {
    "infobase": { "type": "server", "server": "<сервер 1С>", "database": "<имя тестовой ИБ>" },
    "user": { "name": "АдминистраторТакси", "password": "", "interface": "taxi" }
  },
  "infobase": { "type": "server", "server": "<сервер 1С>", "database": "<имя тестовой ИБ>" },
  "users": {
    "АдминистраторKafka": { "name": "АдминистраторKafka", "password": "", "interface": "taxi" },
    "ПользовательKafka": { "name": "ПользовательKafka", "password": "", "interface": "taxi" }
  },
  "mcp": { "serverName": "vanessa", "url": "http://127.0.0.1:9876/mcp", "port": 9876 },
  "features": "../features",
  "results": "./results"
}
```

`users` содержит именованные профили TestClient. В общем профиле поля
`password` пустые. Пути к платформе и параметры тестовой ИБ могут потребовать
изменения при работе на другом компьютере.
Адрес MCP в профиле должен совпадать с настройкой клиента в
`tests/.codex/config.toml`. Схему файловой ИБ и подробную настройку смотрите
в документации установленного плагина.

В интерактивном `interactive.local.json` сохраните `ВыполнитьСценарии` и
`ЗавершитьРаботуСистемы` равными `false`. Менеджер и TestClient запускаются в
режиме «Такси» (`/iTaxi`).

Комьюнити-лицензия ограничивает работу тремя одновременными сеансами:
менеджер и не более двух TestClient. После сценария, прогона, ошибки или остановки
менеджер и использованные клиенты остаются открытыми. Если для следующего запуска
не хватает сеанса, завершайте только ненужный TestClient своего контура. Сначала
сохраните диагностику и восстановите данные, затем убедитесь, что сеанс
фактически завершён. Закрытие окон и отключение клиента от Vanessa не освобождают
сеанс. Чужие сеансы не закрываются; новый административный клиент только для
восстановления связи не запускается.

CLI находится в `scripts/vanessa.mjs` установленного плагина 1C AI Core.
Запускайте его с корнем проекта `tests`; для проверки доступности используйте
`doctor --project-root <путь-к-tests>`, для выбора сценария — `describe` с
путём к feature относительно `tests`. Перед `run` установите фактические эффекты
и необходимое разрешение по инструкции навыка; используйте документированный
файл разрешения. `start` и `setup` также могут запускать приложения или менять
runtime и требуют соответствующего разрешения.

Например, из каталога `tests` после установки пути к плагину:

```powershell
$pluginRoot = '<каталог установленного плагина 1C AI Core>'
node "$pluginRoot/scripts/vanessa.mjs" doctor --project-root . --client 'АдминистраторKafka'
node "$pluginRoot/scripts/vanessa.mjs" describe --project-root . --client 'АдминистраторKafka' --feature 'ui/features/Справочники/Брокеры/ОсновныеОперации.feature' --scenario 'Начальное состояние новой карточки брокера'
```

После проверки и получения требуемого разрешения `run` принимает те же
`--project-root`, `--client`, `--feature` и `--scenario`, а также путь к файлу разрешения
через `--authorization-file`.

Перед запуском проверяйте выбранные файл и сценарий, синтаксис и готовность
стенда. Сценарий запускается с начала; результат относится к конкретному
файлу и варианту. Проверка синтаксиса сама по себе не подтверждает выполнение.

`VAParams.json` остаётся CI-профилем. Для MCP используется отдельный интерактивный
JSON: без автоматического запуска всех сценариев и завершения 1С.
Для сценариев с записью заранее определяются
fixtures и стратегия очистки/восстановления, включая сбой. Допускаются собственные
элементы и данные начальной инициализации по общим правилам `tests/AGENTS.md`.
Сценарии справочника «Брокеры» создают собственные элементы; порядок очистки
и восстановления после сбоя описан ниже.

## Структура каталога тестов

Исполняемые feature-файлы сгруппированы по подсистеме и объекту. Файлы внутри
объекта названы по проверяемой функциональности; числовые префиксы не используются.

```text
features/
├── Справочники/
│   ├── Брокеры/
│   ├── Продюсеры/
│   │   └── ДиспетчерыЗадач/
│   └── Консьюмеры/
│       └── ДиспетчерыЗадач/
├── РегистрыСведений/
│   ├── ОчередьПотоков/
│   ├── ПозицииОпераций/
│   ├── ХэшСуммыСообщений/
│   ├── ИсходящиеСообщения/
│   └── ВходящиеСообщения/
└── Обработки/
    └── ПанельАдминистрирования/
libraries/
recovery/
VAParams.json
```

Такое разделение следует рекомендации Vanessa отделять исполняемые сценарии
от настроек, результатов и переиспользуемых библиотек и группировать их по
подсистемам. Конкретные имена каталогов выбирает проект. Корнем загрузки остаётся
`features`: Vanessa рекурсивно читает вложенные каталоги, поэтому CI-параметр
`КаталогФич` (`/work/features`) сохраняется.

Профиль запуска и интерактивные параметры отслеживаются Git; результаты и
служебные файлы каталога `.vanessa/` исключены из него. CI-настройки — в
`VAParams.json`. Экспортные общие шаги находятся
в `libraries/`, отдельно от исполняемых сценариев `features/`. Для CI в настройках
указан каталог `/work/libraries`: при запуске необходимо смонтировать каталог `ui`
в `/work` вместе с `features` и `libraries`. В интерактивном менеджере добавьте
полный путь к `ui/libraries` на вкладке «Библиотеки», сохранив остальные каталоги.
Имена тестовых элементов формируются внутри каждого сценария.

## Функциональные тесты справочника «Брокеры»

Сценарии с тегом `@Брокеры` находятся в `features/Справочники/Брокеры`.

| Область | Проверки |
| --- | --- |
| Создание и валидация | Начальное состояние, обязательные наименование, узлы, адрес и ключ параметра; отказ записи неполной карточки |
| Узлы | Добавление, копирование отключённого узла, изменение адреса, флаг использования, сохранение порядка и удаления строк после повторного открытия |
| Запись | Повторное открытие, изменение карточки, отражение изменений в списке, независимость копии |
| Параметры | Выбор ключа и отмена выбора, значения по умолчанию, строковый, числовой, булев и списочный типы, смена ключа и удаление строки |
| Редактор параметров | Очистка строки, переключение типа редактора, увеличение и уменьшение числа, запрет копирования строки, подбор ключа по уникальной части имени с проверкой единственного совпадения, подсказки без поискового текста и дублей |
| Форма выбора свойства | Текущий ключ, отмена без потери значения, выбор строки, фильтр важности и его сброс, описание свойства |
| Режим пароля | Маскирование искусственного значения `client.id`, сохранение, повторное открытие, изменение и снятие маскирования |
| Защищённые параметры | Отмена редактирования, удаление и повторное добавление ключа, переход к числовому типу, отсутствие переноса защищённого значения в копию и независимость значений копии и исходного брокера |
| Блокировки | Независимость чтения и публикации, сохранение и индикация в карточке и списке, включая оба смешанных состояния |
| Выбор брокера | Выбор собственного тестового брокера в новых карточках продюсера и консьюмера, отмена выбора для пустого и заполненного поля |
| Права доступа | Чтение подготовленного брокера, запрет создания, копирования, пометки удаления, изменения и управления блокировками для `ПользовательKafka` |

Подключение к Kafka не проверяется. Адреса узлов используют домен `.invalid`;
реальные брокеры, пароли и другие учётные данные для этих тестов не нужны.
Запуск проверки подключения, формирование её журнала и окраска узлов также исключены из этого набора.
Проверка числового редактора использует общий параметр `message.max.bytes`:
уменьшение `1024` до `1023`, увеличение `2048` до `2049` и сохранение обоих
значений после повторного открытия. Допустимость значения параметра определяет
пользователь; проверка границ диапазона не входит в требования к редактору.
После сброса фильтра важности проверяются снятый отбор, исходное количество
свойств и наличие всех трёх уровней важности.

Все административные сценарии явно подключают профиль `АдминистраторKafka`
с соответствующим логином, именем компьютера `localhost` и `/iTaxi`.
`ПраваДоступа.feature` подключает профиль `ПользовательKafka`.
Контекст проверяет имя выбранного профиля и параметры
`/N` и `/iTaxi`; TestClient выбирается явно.
В среде должны быть подготовлены оба пользователя по правилам `tests/AGENTS.md`.
В тестах не используются шаги проверки ролей менеджера Vanessa.
Сценарии прав читают fixture `Брокер по умолчанию` и проверяют отсутствие
команд создания, копирования и пометки удаления в списке. Проверка команд
блокировки создаёт собственного брокера под `АдминистраторKafka`, затем
проверяет отказ обеих команд под `ПользовательKafka` и удаляет свои данные.

Выбирайте начальный профиль TestClient аргументом `--client` и передавайте
его в `doctor`, `describe` и `run`. CLI проверяет процесс и подключение
клиента, но не подтверждает фактического пользователя сеанса 1С. Сценарии прав
проверяют пользователя средствами 1С.

Требуется расширение VAExtension, в том числе для проверки состояния объекта
и подготовки и очистки кеша топиков в сеансе TestClient.

Сценарии формируют собственные имена `VA-Брокеры-…` с UUID или случайными
суффиксами. Записывающие сценарии удаляют свои брокеры и связанные записи
безопасного хранилища после успеха или обычной ошибки; сценарии выбора также
очищают запись кеша собственного брокера. Записи хранилища удаляет обработчик
удаления брокера в конфигурации. Ошибка проверки остаётся в отчёте.
При аварийном обрыве менеджера или сбое самой очистки может потребоваться
адресное восстановление по выведенному имени и ссылке. В проверке пустого
наименования неожиданная запись без ссылки также требует отдельной диагностики.
В сценариях выбора брокера карточка продюсера или консьюмера не записывается; после проверки
изменения отбрасываются. Параметры в режиме пароля содержат только искусственные
строки с префиксом `VA-`. Сценарии сохраняют ожидаемые результаты и при обнаружении
ошибки продукта: успешный синтаксис сам по себе не означает успешного прогона.

Для точечного запуска выберите сценарий «Сохранение повторное открытие и изменение
брокера» в `ui/features/Справочники/Брокеры/ОсновныеОперации.feature` через CLI
плагина и примените описанный выше порядок разрешения и запуска.

Результаты выбранных запусков и run receipts сохраняются в каталоге результатов
локального профиля (`.vanessa/results`).

## UI-тесты продюсеров и консьюмеров

Для `кфкПродюсеры` и `кфкКонсьюмеры` сценарии расположены
в каталогах `features/Справочники/Продюсеры` и `features/Справочники/Консьюмеры`.
Теги объектов — `@Продюсеры` и `@Консьюмеры`.

| Файл в каждом каталоге | Пользователь | Проверки |
| --- | --- | --- |
| `ОсновныеОперации.feature` | `АдминистраторKafka` | Чтение подготовленного элемента, его брокера и топика, пустые поля и список объектов/топиков новой карточки |
| `СохранениеИРедактирование.feature` | `АдминистраторKafka` | Создание с записью и отдельный сценарий изменения собственного записанного элемента; повторное открытие по ссылке и проверка реквизитов и табличной части, обновление имени в списке |
| `Параметры.feature` | `АдминистраторKafka` | Выбор ключа из формы свойств librdkafka, добавление и изменение строк, удаление одной строки с сохранением остальных; замена изменённой таблицы стандартными параметрами без дублей, проверка после повторного открытия |
| `ДополнительныеНастройки.feature` | `АдминистраторKafka` | Сохранение включённого и снятого флага дедупликации продюсера или идемпотентной обработки консьюмера; изменение и удаление одной из нескольких строк объектов/топиков с сохранением остальных |
| `Обработчики.feature` | `АдминистраторKafka` | Общие настройки и переопределения строк для произвольного обработчика и Конвертации данных; подтверждение/отмена ввода метода, наследуемое отображение, видимость полей, сохранение неактивных настроек после смены типов |
| `Валидация.feature` | `АдминистраторKafka` | Обязательные реквизиты и строки объектов/топиков, обязательные колонки таблиц, отказ записи с несуществующим брокером; у консьюмера — отклонение нулевого тайм-аута и восстановление предыдущего значения после отмены ввода |
| `КопированиеИПометкаУдаления.feature` | `АдминистраторKafka` | Копирование из списка, перенос настроек, сохранение и независимость копии после повторного открытия |
| `Блокировки.feature` | `АдминистраторKafka` | Независимость регистрации, сериализации и публикации продюсера, чтения и десериализации консьюмера; все сочетания, запись, колонки списка, отметки команд и предупреждения после повторного открытия |
| `ДиспетчерыЗадач/*.feature` | `АдминистраторKafka` | Чтение подготовленной группы, начальное состояние и отмена создания; создание и изменение с повторным открытием; независимость копии, отмена/установка/снятие пометки удаления; обязательное наименование и отклонение отрицательных счётчиков подпотоков; перемещение собственного элемента между своими диспетчерами и в корень |
| `ПраваДоступа.feature` | `ПользовательKafka` | Отсутствие команд создания элемента и диспетчера, копирования и пометки удаления; чтение подготовленного элемента и диспетчера задач в режиме «только просмотр» |

Требуются группа `Диспетчер задач`, `Продюсер: ТестовыйСправочник`,
`Консьюмер: ТестовыйСправочник` и `Брокер по умолчанию`, подготовленные по
правилам `tests/AGENTS.md`. Сценарии включают плоский режим списка перед выбором элемента,
чтобы не зависеть от раскрытой группы.
Все подключения явно задают пользователя и `/iTaxi` и проверяют выбранный профиль.

Элемент справочника и его группа проверяются отдельно. Группа — диспетчер задач:
в её карточке доступны наименование и число подпотоков обработки/транспорта.
Команд блокировок регистрации, сериализации, публикации, чтения и десериализации
у группы нет; административные сценарии проверяют отсутствие применимых имён команд.
Поля брокера, топиков и параметров элемента не переносятся в ожидания для группы.
Это правило действует для существующих и будущих тестов согласно `tests/AGENTS.md`.

Сценарии групп используют собственные имена `VA-Диспетчеры-Продюсеры-<суффиксы>`
и `VA-Диспетчеры-Консьюмеры-<суффиксы>`. Записывающие сценарии после успеха
или обычной ошибки удаляют собственные элементы и пустые группы с проверкой имени,
ссылки и отсутствия дочерних элементов. Подготовленный диспетчер и его дочерние
элементы не изменяются. Проверки сохранения, копии и пометки удаления включают
повторное открытие карточки и проверку счётчиков. При неожиданной записи
группы без имени в негативной проверке требуется отдельная диагностика:
у такой группы нет уникального имени для адресной очистки.

Сценарии `ОсновныеОперации.feature` и `ПраваДоступа.feature` не записывают данные.
Проверка отмены формирует уникальное имя с префиксом
`VA-Продюсеры-` или `VA-Консьюмеры-`, проверяет его отсутствие перед созданием
карточки и отбрасывает изменения при закрытии. При сбое нужно закрыть оставшуюся
новую карточку без сохранения; повторная инициализация общих fixtures не нужна.
Сценарии `СохранениеИРедактирование.feature` создают собственные элементы с именами
`VA-Продюсеры-Запись-<суффиксы>` и `VA-Консьюмеры-Запись-<суффиксы>`, уникальными
топиками и идентификатором группы консьюмера. Элементы создаются вне диспетчера задач.
Проверяются имя, брокер и табличная часть; у продюсера — также идемпотентная отправка,
у консьюмера — ИД группы и тайм-аут. Сценарий изменения создаёт и повторно открывает
элемент, меняет значения, записывает и открывает его ещё раз.

Записывающие сценарии элементов создают собственного брокера, синхронно
подготавливают кеш топиков в сеансе TestClient перед выбором и повторным открытием,
а после успеха или обычной ошибки удаляют собственные элемент, брокер и запись кеша.
Сценарии чтения подготовленного элемента сохраняют и восстанавливают исходный кеш
общего брокера в соответствующем сеансе TestClient. Очистка не удаляет продюсера
с исходящими или консьюмера с входящими сообщениями. Повторная инициализация общих
fixtures не используется. Сценарии не проверяют обмен с Kafka.
Перед открытием карточки с непустым брокером необходимо подготовить кеш топиков
в сеансе TestClient: иначе форма может обратиться к Kafka.

В `Параметры.feature` каждый сценарий создаёт собственный элемент
`VA-Продюсеры-Параметры-<суффиксы>` или `VA-Консьюмеры-Параметры-<суффиксы>`.
Первый сценарий выбирает дополнительный ключ из формы свойств librdkafka
(`acks` у продюсера, `fetch.min.bytes` у консьюмера), добавляет строку, меняет
значения исходной и добавленной строк, затем удаляет только добавленную строку.
После каждой записи проверяется отсутствие несохранённых изменений; после
итогового открытия — оставшееся значение `message.timeout.ms` или `auto.offset.reset`.
Второй сценарий записывает изменённый набор и восстанавливает стандартную таблицу:
`message.timeout.ms = 5000` у продюсера и `auto.offset.reset = earliest` у консьюмера.
Повторное применение команды не добавляет дубли; результат проверяется после записи
и повторного открытия. Карточка остаётся открытой между изменениями.
Сценарии удаляют собственные данные и кеш после успеха или обычной ошибки.
Общие fixtures и диспетчеры задач не изменяются; у диспетчеров нет проверяемых
таблиц параметров.

В `ДополнительныеНастройки.feature` снятый флаг проверяется после перечитывания,
установленный — после итогового открытия. Из нескольких объектов/топиков меняется
первая строка, удаляется вторая, затем проверяется оставшаяся строка.
`Обработчики.feature` использует существующие имена методов и настройки Конвертации
данных расширения `examples`, сохраняя их только в собственных карточках.
Сериализация, десериализация и обмен с Kafka не запускаются. Пустые настройки строки
показывают общий обработчик; явные значения строки проверяются отдельно, включая
сохранение неактивных настроек после смены типа и повторного открытия.

В текущей форме поле `РежимАсинх` продюсера и поле `ДвоичныеДанные` консьюмера
скрыты. Сценарии проверяют их скрытость; переключение этих режимов и влияние
асинхронного режима на параметры через данный UI не покрываются.

`ДиспетчерыЗадач/Иерархия.feature` создаёт две собственные группы и элемент.
Элемент создаётся из иерархического списка внутри A; родитель A проверяется до записи.
Затем элемент перемещается в B и в корень. После промежуточных записей
выполняется перечитывание, после последней — повторное открытие.
После проверки или обычной ошибки удаляются собственный элемент, затем пустые
группы и брокер.

`ДиспетчерыЗадач/НепустыеГруппы.feature` создаёт собственные группу, дочерний элемент
и копию группы. Проверяются состав области копии, сохранение счётчиков и исходного
родителя ребёнка. Отмена пометки сохраняет все три объекта; установка и снятие
пометки оригинальной группы каскадируются на её ребёнка, оставляя копию независимой.
Состояние каждого объекта и содержимое ребёнка читаются отдельно на каждом этапе.
После успеха или обычной ошибки сценарий удаляет собственный элемент, затем пустые
группы и брокер. Подготовленные группы не меняются.

В `Валидация.feature` каждый сценарий начинает с заполненной собственной новой карточки
`VA-Продюсеры-Валидация-<суффиксы>` или `VA-Консьюмеры-Валидация-<суффиксы>` и изменяет
только проверяемые поля. Сообщения перед каждой попыткой записи очищаются и сравниваются
с точным ожидаемым списком. Проверяются обязательность имени и брокера, ИД группы
консьюмера, непустой список объектов/топиков, тип объекта, ключ и значение параметра
продюсера, топик и ключ параметра консьюмера. Несуществующая ссылка брокера должна
блокировать запись; нулевой тайм-аут — вызывать ошибку ввода до записи.
Перед проверкой пустой таблицы сценарий явно выбирает и удаляет подготовленную строку,
затем проверяет, что количество строк равно нулю. Та же подготовка выполняется перед
добавлением строки с незаполненными обязательными колонками.
После отказа карточка остаётся новой; сценарий отбрасывает изменения и проверяет
отсутствие элемента в обновлённом списке. Подготовленные данные не изменяются.
Сценарии удаляют неожиданно записанный собственный элемент, в том числе без имени —
по точной ссылке своего брокера; общие fixtures не переинициализируются.
Формат топиков и параметров Kafka этими проверками не валидируется.

В `КопированиеИПометкаУдаления.feature` сценарий копирования создаёт собственный
исходный элемент `VA-Продюсеры-КопияУдаление-<суффиксы>` или
`VA-Консьюмеры-КопияУдаление-<суффиксы>`. Сценарий копирования создаёт также элемент
с суффиксом `-копия`, проверяет перенос брокера, объектов/топиков, параметров и
дополнительных настроек. Затем меняет топик и идемпотентность продюсера либо топик,
ИД группы и тайм-аут консьюмера. После записи проверяет разные ссылки исходника и
копии, оба имени в списке, сохранение изменений копии и неизменность исходника.
Ссылки исходника и копии запоминаются сразу после записи. Сценарии удаляют оба
элемента и собственного брокера после успеха или обычной ошибки. Отдельный
сценарий элемента проверяет отмену пометки, установку и снятие пометки с
проверкой состояния после открытия. Общие fixtures не изменяются.

В `Блокировки.feature` два сценария продюсеров покрывают все восемь сочетаний
регистрации, сериализации и публикации. Сценарий консьюмера покрывает все четыре
сочетания чтения и десериализации. После каждого переключения выполняется команда
«Записать», проверяется отсутствие несохранённых изменений, обновляется список
и проверяются все колонки блокировок (`Р`, `С`, `П` или `Ч`, `Д`). Между списком
и карточкой тест переключается активизацией уже открытых окон. Карточка остаётся
открытой на протяжении всех изменений: используется её существующая блокировка
редактирования. После закрытия формы 1С может удерживать блокировку ещё до 10 секунд.
В карточке для каждого сочетания проверяются отметки команд и предупреждения.
В конце карточка закрывается и один раз открывается по сохранённой ссылке:
повторно проверяются имя, сохранённое состояние всех блокировок и отсутствие
несохранённых изменений. Дальнейшего редактирования после этого открытия нет.
Каждый сценарий использует собственный элемент `VA-Продюсеры-Блокировки-<суффиксы>`
или `VA-Консьюмеры-Блокировки-<суффиксы>`, созданный вне диспетчера задач с исходно
снятыми блокировками. В конце проверяется, что все блокировки вновь сняты.
Сценарии удаляют свой элемент и брокера после успеха или обычной ошибки. Общие
настройки и блокировки fixtures не изменяются.

Для запуска используется тот же CLI с административным профилем. Сценарии прав
сами подключают TestClient `ПользовательKafka`, проверяют ограничения
в его сеансе и оставляют его открытым для следующих сценариев.
`АдминистраторKafka` также остаётся открытым; следующий сценарий подключается
к нужному пользователю. При сбое клиенты не завершаются; данные эти сценарии не меняют.
Для точечного запуска можно выбрать «Начальное состояние новой карточки продюсера»
в `ui/features/Справочники/Продюсеры/ОсновныеОперации.feature` или «ПользовательKafka
читает подготовленного консьюмера без возможности изменения» в
`ui/features/Справочники/Консьюмеры/ПраваДоступа.feature`.

Оба пользователя должны запускаться без блокирующих стартовых окон. В контуре
с лицензией разработчика платформа может показывать информационное уведомление
при каждом новом сеансе. Его нужно подтвердить до истечения тайм-аута подключения
TestClient; тайм-аут до подключения не является результатом проверки прав.
Новые сценарии требуют проверки синтаксиса в Vanessa и прогона с начала;
наличие feature-файлов само по себе не подтверждает их успешное выполнение.

## Панель администрирования

Сценарии в `features/Обработки/ПанельАдминистрирования` проверяют основную форму,
фоновые и регламентное задания, очереди, логирование и ограничения прав.
[Постоянная инструкция](docs/administration-ui-tests.md) описывает подготовку
стендов, отбор и запуск, долговременные снимки настроек и восстановление после
ошибки или аварии. Для явного восстановления есть отдельный сценарий
`recovery/ПанельАдминистрирования.feature` вне обычного набора.

## Служебные регистры

В `features/РегистрыСведений` находятся сценарии для `кфкОчередьПотоков`,
`кфкПозицииОпераций` и `кфкХэшСуммыСообщений`. Для каждого регистра проверяются
отображение обычной и граничной комбинированных меток в списке и карточке,
доступ административного пользователя и ограничения чтения/аудита.
В позициях операций дополнительно проверяется представление операции сериализации
и собственного раздела; в хэш-суммах — ключ записи и хэш.
В `ПозицииОпераций/ПредставленияОпераций.feature` находятся девять примеров для
остальных известных операций и отдельный сценарий для неизвестного идентификатора:
карточка показывает «Неизвестная операция», исходный UUID, раздел и компоненты метки.
Эти проверки выполняются под `АдминистраторKafka` с собственными записями.

Записи подготавливаются программно в базе менеджера. Менеджер и оба TestClient
должны использовать общую подготовленную тестовую базу unit-контура. Метки создаются через
`НоваяКомбинированнаяМетка()` и `ГраничнаяКомбинированнаяМетка()` общего модуля
`кфкОбщегоНазначенияСлужебный`; ожидаемые компоненты получают его методами
расшифровки. Проверяется привязка и отображение полей UI, а не алгоритмы этих
методов. Список показывает дату GMT, карточка — результат
`ДатаИзКомбинированнойМетки()` с учётом часового пояса сеанса.

Каждый сценарий создаёт запись с уникальным ключом `VA-Регистры-<UUID>`.
При обычном выполнении запись удаляется через список с отбором по ключу; после
ошибки менеджер выполняет адресную очистку по ключу и UUID прогона. Команда
копирования администратора проверяется действием: форма отклоняет добавление;
у ограниченного пользователя команда отсутствует. Использованные TestClient и
менеджер остаются открытыми. При аварийном обрыве менеджера или сбое самой очистки
используйте удаление из списка с отбором по выведенным ключу, UUID и метке прогона;
для очереди все три значения входят в ключ записи. Общие настройки обмена,
тестовые объекты и остальные служебные записи не изменяются.

### Исходящие и входящие сообщения

Сценарии находятся в `features/РегистрыСведений/ИсходящиеСообщения` и
`features/РегистрыСведений/ВходящиеСообщения`.

| Feature | Сообщения | Прикладные проверки |
| --- | --- | --- |
| `ПросмотрИОчередь.feature` | Исходящие и входящие | Оба пользователя, реквизиты, заголовки, журнал, содержимое JSON, пустые разделы, доступность обработки при множественном выделении и возврат в очередь |
| `УдалениеИГрупповыеКоманды.feature` | Исходящие и входящие | Подтверждение и отмена удаления выделенных и отфильтрованных сообщений, отсутствие отбора, выделения или совпадений, отмена полной очистки, права, групповой возврат |
| `РучнаяОбработка.feature` | Исходящие и входящие | Успешная обработка и ошибка отсутствующего правила из списка и карточки, обновление счётчика, даты и метки, сохранение журнала и соседних сообщений |
| `ЗапретРучныхКомандПриФоновомОбмене.feature` | Исходящие и входящие | Запрет ручной обработки и удаления при включённом фоновом обмене |
| `МеткиСообщений.feature` | Исходящие и входящие | Компоненты меток регистрации или загрузки и изменения, обычные и граничные метки, дата GMT списка, оба пользователя |
| `СнимкиИсходныхДанных.feature` | Исходящие | Снимок объекта и записи тестового регистра, ссылки на существующий и удалённый объект, ошибка восстановления XML |
| `ИсторияВыгрузки.feature` | Исходящие | История из списка и карточки тестового объекта для обоих пользователей, все метки объекта и исключение чужого сообщения |
| `ПолнаяОчисткаИзолированногоРегистра.feature` | Исходящие и входящие | Подтверждённая полная очистка после самостоятельной подготовки пустого регистра |

Менеджер и TestClient должны работать в одной ИБ с инициализированными данными
и пользователями. Большинство сценариев требуют остановленного фонового обмена
и отсутствия активных потоков. Сценарии с тегом `@ФоновыйОбменВключён` тоже начинают
с остановленного обмена. Они сохраняют использование и расписание задания и блокировку
интеграции, затем временно включают задание с расписанием на 01.01.3999. Перед очисткой
собственных сообщений задание выключается; исходные настройки восстанавливаются и
проверяются как после успеха, так и после обычной ошибки. Параллельные прогоны и ручное
изменение настроек во время сценария недопустимы. При аварийном завершении менеджера
восстановите настройки по выведенному `ИсходноеСостояниеФоновогоОбмена`, затем удалите
записи по выведенным собственным ключам.

Сценарии с тегом `@ИзолированнаяИБ` выполняются в тестовой ИБ без параллельных
записей. Перед проверкой они очищают целевой регистр целиком, включая ранее существовавшие
записи; эти записи не восстанавливаются. Регламентное задание и блокировка
интеграции не изменяются: до начала обмен должен быть остановлен.
Собственные записи удаляются после успеха или обычной ошибки.

Используются подготовленные `Продюсер: Общий`, `Консьюмер: Общий` и настройки
тестового справочника. Fixtures сообщений создаются программно: добавление и изменение записей
через формы регистров запрещены. Две записи имеют один
`КлючЗаписи` и разные метки, третья — контрольный ключ. Проверяемые команды
выполняются через UI соответствующего пользователя Kafka. Подключение к брокерам
не требуется; успешная ручная обработка использует обработчики расширения `examples`.

Fixtures сериализуют исходные данные, заголовки и тело сообщения методом
`кфкОбщегоНазначенияСлужебный.ЗначениеВХранилище()`: формы ожидают XML внутри хранилища.
Поля, заголовки и тело проверяются
через форму записи, без отдельного чтения регистра кодом.
Для входящей ручной обработки JSON создаётся методом этого же модуля `ЗначениеВJSON()`.
Прямое создание хранилища исходных данных оставлено для двух специальных проверок:
отсутствующего снимка и некорректного XML. История получает ключи методом
`кфкОбработкаСобытийСлужебный.КлючЗаписиИсходящихСообщений()`.
Остальные fixtures записываются напрямую, чтобы задать точные ключи, метки,
статусы и счётчики; регистрация через `ПоместитьВОчередьИсходящих()` формирует
их самостоятельно и не заменяет такую подготовку.

Снимки тестового справочника и тестового РС без ссылок не требуют записи самих объектов.
Сценарии снимков по ссылке создают собственный элемент тестового справочника;
вариант удалённого объекта удаляет его после сохранения снимка и до открытия карточки.
Для ссылочного режима проверяется недоступность вкладок снимка, видимость правильной
ссылки на существующий объект и её отсутствие после удаления.
История создаёт собственный элемент тестового справочника, а входящая ручная
обработка создаёт его из JSON. UUID назначается заранее и выводится до записи;
при подготовке и удалении собственного элемента регистрация обмена отключается.
Общие шаги из `libraries/ФикстурыСообщенийKafka.feature` создают повторяющийся набор.
После успеха или обычной ошибки `libraries/ОчисткаСообщенийKafka.feature` удаляет
сообщения, очередь и при необходимости собственный тестовый объект. Очистка проверяет
UUID и точные ключи; историю очищает по вычисленному для тестового объекта ключу.
Проверяемые команды удаления выполняются через UI. Физическое удаление
объекта в подготовке и очистке нужно для сценария удалённой ссылки. Общие fixtures
и диспетчеры задач не меняются; менеджер и TestClient остаются открытыми.
При аварийном обрыве менеджера или сбое самой очистки используйте выведенные ключи
и UUID для отдельного восстановления.
В выборе брокера пустой кеш топиков заполняется в самом TestClient через VAExtension;
алгоритм попадания в кеш, включая пустой список, проверяется YAxUnit.
Сценарии истории дополнительно выводят вычисленный
ключ сообщений после создания объекта. Переинициализация общих fixtures не используется.
